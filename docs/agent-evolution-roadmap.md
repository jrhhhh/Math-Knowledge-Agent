# Math-Agent 向可验证数学智能体演进路线

## 1. 目标

将 Math-Agent 从“带知识检索、会话记忆和质量护栏的数学问答应用”，逐步建设为能围绕数学问题选择有限工具、保存推理状态、核对关键结论，并清楚说明证据边界的受控数学智能体。

首要原则是：系统不能把语言模型生成、结构完整度、数值检查、符号检查、形式化验证和人工审核混为同一种“正确”。每个结论都应标示它由什么方法、在什么条件下得到支持。

## 2. 当前基础与主要缺口

项目已经具备：

- SQLite 持久化会话、知识点、学习记录、回答记录和重试任务；
- 本地知识点与人工审核教材片段检索；
- 证明审查入口、公式格式修复、回答结构完整度检查；
- 主模型、备用模型、本地模板兜底，以及持久化重试队列；
- 请求预算、错误记录、管理审计和前端会话工作台。

当前主要缺口：

1. 回答完整度不是数学正确性，但部分界面状态容易被理解为“证明已通过”；
2. 数学工具主要限于内部检索和规则检查，尚不能执行精确计算、符号验证、反例搜索或形式化证明；
3. 会话摘要不能替代结构化的子目标、假设、失败路径和验证报告；
4. 问答流程基本由后端固定，模型不能在受控范围内选择“检索、计算、找反例、审查、修订”等下一步行动；
5. 现有停止条件主要是时间和重试次数，尚缺少任务目标是否满足的验收条件。

## 3. 总体架构

```text
用户问题 / 已保存对话
          │
          ▼
任务控制器 ───────► 问题状态（目标、假设、子目标、预算）
    │                         │
    │  选择受限动作            │  读取相关状态与证据
    ▼                         ▼
工具执行器 ───────► 证据库（原始输出、适用范围、版本）
    │
    ▼
审查与终止判定 ───► 回答、未解决项、可追溯证据
```

职责边界：

- **任务控制器**：维护状态、预算和停止条件；只允许白名单动作。
- **语言模型**：提出下一步行动、组织解释、草拟证明和定位可能缺口；其输出默认是待验证信息。
- **工具执行器**：执行参数受约束的检索、计算和验证；保存原始结果与失败原因。
- **审查模块**：检查前提、结论、证据关系和任务状态；不能仅凭模型自评宣布完成。
- **前端**：展示当前子目标、证据类型、证据范围和未解决事项。

## 4. 分阶段执行路线

### M1：统一可信度状态并建立评测基线

**目的**：先让系统准确表达“知道什么、不知道什么”，避免把结构信号当作数学正确率。

**实施内容**：

1. 为回答、证明步骤和结论增加可组合的证据状态：
   - `unverified`：语言模型生成，尚未独立核验；
   - `model_reviewed`：模型审查未发现指定类型的问题；
   - `computed`：有限范围内的精确或数值计算通过；
   - `symbolically_verified`：指定表达式及假设下的符号检查通过；
   - `formally_verified`：形式化证明器检查通过；
   - `human_reviewed`：人工审核结论已记录。
2. 每条证据保存：验证对象、适用假设、输入、输出摘要、方法、执行时间、答案版本和状态。
3. 将当前 `answer_quality` 明确为“结构完整度”；保留已有接口字段，新增证据字段后再更新前端展示。
4. 证明审查界面把“通过”改为准确的模型审查措辞，并允许 `uncertain` 状态。
5. 使用已有章节基准题建立人工审核基线；补充“结构完整但结论错误”的对抗样例。

**验收条件**：

- 结构完整度不会自动转化为数学正确性；
- 用户可查看每个“已验证”状态的对象、条件和依据；
- 基准评测报告分别统计结构完整度、人工正确性和证据覆盖率；
- 旧版 `/ai/ask` 和对话接口保持兼容。

### M2：接入受限数学工具，建立可复现检查闭环

**目的**：让系统能实际执行明确的数学检查，而不是仅通过文本联想给出结果。

**首批工具范围**：

| 工具 | 处理范围 | 可支持的结论 |
| --- | --- | --- |
| 教材检索 | 已导入且人工审核的片段 | 原文、页码、审核状态 |
| 精确计算 | 整数、有理数、小规模矩阵 | 特定计算结果 |
| 符号检查 | 白名单表达式的代数恒等式 | 给定假设下的恒等式 |
| 反例检查 | 明确有限域、范围或候选点 | 找到反例可否定原命题 |

**实施内容**：

1. 建立统一 `ToolRequest` / `ToolResult` 数据结构，包含工具名、版本、输入、资源预算、状态、原始输出与证据摘要。
2. 工具必须使用结构化参数，不直接执行模型生成的任意代码或 Shell 命令。
3. 对表达式检查定义变量域、禁止函数和最大复杂度；对计算定义大小、时间和内存上限。
4. 在任务控制器中检查“工具问题是否覆盖用户命题”：例如只验证正整数样本，不能支持“所有实数”的结论。
5. 工具执行失败、表达式不支持、超时和定义域不清时，写入证据但不得产生“验证通过”。

**验收条件**：

- 所有工具结果都能从保存的输入重放；
- 支持的示例题在独立运行中得到相同结果；
- 除零、定义域缺失、超时和不支持输入都有明确状态；
- 用户界面能区分“找到反例”和“有限范围内未找到反例”。

### M3：建立问题级结构化记忆

**目的**：让长问题的关键条件、探索轨迹和验证结果可恢复、可检索、可撤回。

**核心数据对象**：

| 对象 | 主要字段 |
| --- | --- |
| `agent_tasks` | 原始问题、目标、状态、会话 ID、预算、终止原因 |
| `agent_subgoals` | 子目标、依赖项、状态、优先级、提出依据 |
| `agent_claims` | 命题、假设、状态、来源、依赖结论 |
| `agent_events` | 行动、输入、输出摘要、错误、耗时、轮次 |
| `verification_reports` | 验证方法、对象、条件、结果、原始证据引用 |

**实施内容**：

1. 将现有会话 ID 写入任务与事件，延续重试队列对 `conversation_id` 的关联方式。
2. 上下文构建改为“任务目标与假设 + 相关子目标与证据 + 最近消息”，会话摘要只作为辅助信息。
3. 为命题建立依赖关系；若某个前提被反驳或撤回，所有依赖结论自动标为待复核。
4. 任务和事件使用追加式记录；对状态变更保留原因和时间线。
5. 服务重启后恢复未终止任务，但不自动突破原有预算或权限范围。

**验收条件**：

- 服务重启、请求失败和人工重试后都能恢复同一任务状态；
- 长对话中的关键假设不会仅因摘要截断而丢失；
- 对某个已否定引理的依赖结论可以被定位并重审；
- 重复提交不会生成重复的有效证据记录。

### M4：实现受控自主循环

**目的**：让模型在有限、可审计的动作集合内根据当前证据选择下一步。

**首版动作白名单**：

```text
检索教材 → 提出子目标 → 精确计算 → 符号检查 → 搜索反例
        → 草拟证明 → 模型审查 → 修订结论 → 结束或请求补充条件
```

**执行规则**：

1. 模型必须输出结构化行动计划：行动名称、目标、参数、预期获得的信息和理由。
2. 控制器检查行动是否合法、参数是否完整、是否重复、是否在预算内。
3. 工具结果和审查结果写入事件与证据库，再作为下一轮输入。
4. 每轮评估是否已有足够证据完成、是否发现反例、是否缺少必要条件、是否陷入重复。
5. 单任务设置最大轮数、总时间、模型调用次数和工具调用次数；具体阈值由 M1 基线和 M2 运行数据确定。

**终止状态**：

- `completed_with_evidence`：满足该题型的完成条件，并附带证据；
- `refuted`：已找到满足前提的反例；
- `needs_clarification`：缺少定义域、条件或任务目标；
- `inconclusive`：已有分析但证据不足；
- `budget_exhausted`：达到轮数、时间或调用预算；
- `failed`：不可恢复的系统或工具错误。

**验收条件**：

- 工具结果可以改变下一轮行动；
- 找到有效反例后不继续为原命题构造“证明”；
- 检测到重复行动或预算耗尽时正常结束并保留工作状态；
- 不以“模型声称已经证明”作为唯一完成依据。

### M5：产品化界面与渐进式启用

**目的**：将过程和证据以适合学习场景的方式展示，并只在已验证题型上逐步放量。

**界面内容**：

- 当前目标、假设和子目标；
- 工具执行与教材出处；
- 已验证结论、适用范围和未解决项；
- 发现的反例或条件缺失；
- 停止、继续、补充条件和转人工审核入口。

保留现有快速问答。复杂证明或需要验证的任务使用“深入分析”入口，避免增加普通问答的延迟和成本。

**验收条件**：

- 用户无需了解后端细节，也能判断结论的证据强度；
- 在选定题型上与现有问答对比，人工审核的正确性、误报率、耗时和成本都有可量化数据；
- 达到预设门槛后才扩大工具与题型范围。

## 5. 建议的首个可交付版本

第一版范围限定为 **M1 + M2**：

1. 将回答完整度、模型审查、人工审核和工具验证分开显示；
2. 为回答与证明步骤保存统一证据记录；
3. 接入本地精确计算、受限符号恒等式检查和有限范围反例检查；
4. 在现有问答结果中展示证据和适用条件；
5. 用人工审核基准题和新增工具题完成端到端评测。

该版本能够完成“理解条件 → 执行检查 → 核对结论 → 展示证据”的可验证闭环，同时不要求立即引入复杂的多轮自主循环或形式化证明器。

## 6. 后续技术选择

工具按题型逐步扩展：

- SymPy 或受控内部实现：代数恒等式、微积分局部检查；
- SageMath：数论、群论、有限域和组合问题；
- OSQP / CVXPY：优化问题的数值或凸性验证；
- Lean：高价值定理的形式化验证。

任何工具接入都应先声明其能证明什么、不能证明什么，并在 M1 的证据模型中落地。数值结果通常只支持数值层面的结论；找不到反例不等于命题为真；形式化证明只覆盖已经形式化的陈述和所用公理环境。

## 7. 实施纪律

1. 每个里程碑先定义可复现的验收题，再编写功能；
2. 保留当前 `/ai/ask`、会话和重试接口的向后兼容；
3. 使用功能开关逐步启用新控制器与工具；
4. 对工具调用、模型决定和状态变更记录审计事件；
5. 真实数学正确性指标只来自明确的验证器或人工审核，不能从模型自评推断。

## 8. 当前实现状态（2026-09-25）

### 已完成

- M1：回答证据模型、结构完整度与数学正确性的区分、教材来源证据接口；
- M2：受限整数与有理数精确计算、自然语言算式提取、有限整数区间反例搜索、工具能力探测；
- M3：任务目标、追加式任务事件、终止原因、证据摘要和任务事件接口；
- M4：受限动作规划、单步执行、最多 8 步本地循环、工具结果回写；
- M4：证明模型审查、答案修订、一次“审查—修订—再审查”闭环；
- M5：`agent_mode` 问答开关、受控验证证据面板和 Agent 过程时间线；
- Lean 最小适配：登记 theorem 模板的本地编译验证，并已接入 Agent 和 `/ai/ask`。

### 部分完成

- Lean 目前只支持登记的固定 theorem 模板，不接受任意用户代码；
- Agent 的证明审查和修订仍依赖语言模型，结果状态是 `model_reviewed` 或 `model_revised`；
- 反例搜索只覆盖有限整数区间，区间内未找到反例不等于命题成立；
- SageMath、OSQP、SymPy 和 CVXPY 通过能力探测接口报告状态，但尚未接入执行器。

### 待接入

- 更完整的 Lean 项目级 theorem 形式化和证明文件管理；
- SageMath、OSQP/CVXPY 等题型专用工具；
- 子目标、失败路径和验证报告已分别通过 `agent_subgoals`、`agent_failed_paths` 和 `agent_verification_reports` 持久化；
- 基于工具结果的更丰富动态动作选择与前端交互。
